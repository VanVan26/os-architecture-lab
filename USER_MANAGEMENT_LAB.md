## 1. Теоретический фундамент подсистем безопасности ОС

### 1.1. Триада безопасности: Идентификация, Аутентификация, Авторизация (AAA)
1. **Идентификация (Identification):** заявление о том, кем является субъект (ввод логина: `ivan`, `admin`).
2. **Аутентификация (Authentication):** проверка подлинности субъекта (пароль, SSH-ключ, биометрия, Kerberos-тикет).
3. **Авторизация (Authorization):** проверка полномочий аутентифицированного субъекта на выполнение конкретного действия над объектом (чтение, запись, исполнение, удаление).

---

### 1.2. Модели разграничения доступа
* **DAC (Discretionary Access Control — Избирательное управление доступом):** владелец объекта (файла/каталога) сам определяет права доступа для других пользователей. Это базовая модель в Linux, macOS и Windows.
* **MAC (Mandatory Access Control — Мандатное управление доступом):** доступ регулируется жесткими метками конфиденциальности на уровне ядра (SELinux, AppArmor в Linux; Integrity Levels в Windows). Пользователь не может передать права в обход политики безопасности.
* **RBAC (Role-Based Access Control — Ролевое управление доступом):** права назначаются не отдельным пользователям, а ролям (группам: `developers`, `devops`, `auditors`). Пользователи включаются в группы и наследуют их привилегии.

---

### 1.3. Архитектурные различия идентификаторов субъектов

| Параметр | POSIX (Linux) | macOS (Darwin / XNU) | Windows NT |
| :--- | :--- | :--- | :--- |
| **Идентификатор пользователя** | **UID** (User ID, целое число 32-бит, `0` = root) | **UID** (`0` = root, `501+` = обычные пользователи) | **SID** (Security Identifier, напр. `S-1-5-21-...-1001`) |
| **Идентификатор группы** | **GID** (Group ID, целое число 32-бит) | **GID** (`0` = wheel, `20` = staff, `80` = admin) | **SID группы** (напр. `S-1-5-32-544` = Администраторы) |
| **Хранилище учетных записей** | Плоские файлы: `/etc/passwd`, `/etc/shadow`, `/etc/group` | Служба каталогов Open Directory (`dscl`, `/var/db/dslocal/nodes/Default/`) | База SAM (Security Account Manager) в реестре `HKLM\SAM` или Active Directory (NTDS.dit) |
| **Модель прав доступа** | Стандарт POSIX (rwx для u/g/o) + POSIX ACL (`setfacl`) | Стандарт POSIX (rwx) + Apple NFSv4-style ACLs (`chmod +a`) | NTFS ACL (DACL — Discretionary Access Control List) |
| **Эскалация привилегий** | Подсистема `sudo` (`/etc/sudoers`) | Подсистема `sudo` + GUI Authorization Services | UAC (User Account Control) + `Run as Administrator` |

## 2. Руководство по выполнению для LINUX

*(Подходит для Ubuntu, Debian, Astra Linux, ALT Linux, РЕД ОС, Fedora, Arch Linux)*

### 2.1. Анатомия учетных записей в Linux
Вся информация о пользователях хранится в трех системных файлах:

1. **`/etc/passwd`** — публичный реестр учетных записей (доступен для чтения всем):
   ```
   ivan:x:1001:1001:Ivan Brazhnikov:/home/ivan:/bin/bash
     │  │   │    │          │            │          └─ 7. Командная оболочка (Shell)
     │  │   │    │          │            └──────────── 6. Домашний каталог
     │  │   │    │          └───────────────────────── 5. Комментарий (GECOS: ФИО, телефон)
     │  │   │    └──────────────────────────────────── 4. Основной GID (Primary Group)
     │  │   └───────────────────────────────────────── 3. UID пользователя
     │  └───────────────────────────────────────────── 2. Флаг пароля ('x' = пароль зашифрован в /etc/shadow)
     └──────────────────────────────────────────────── 1. Имя пользователя (login)
   ```

2. **`/etc/shadow`** — защищенный файл хэшей паролей (права `0640` или `0000`, доступен только root):
   ```
   ivan:$6$qZ7yX8L9$AbCdEf...:19820:0:90:7:::
     │  └──────────┬─────────┘   │   │  │  │└─ 8. Дата истечения учетной записи
     │             │             │   │  │  └── 7. Период предупреждения до смены пароля (дни)
     │             │             │   │  └───── 6. Максимальный срок действия пароля (дни)
     │             │             │   └──────── 5. Минимальный интервал смены пароля
     │             │             └──────────── 4. Дата последней смены пароля (дни с 01.01.1970)
     │             └────────────────────────── 2. Алгоритм ($6$ = SHA-512) + соль + хэш
     └──────────────────────────────────────── 1. Имя пользователя
   ```

3. **`/etc/group`** — реестр групп:
   ```
   developers:x:1005:ivan,anna,sergey
        │     │  │         └─ Список дополнительных членов группы
        │     │  └─────────── GID группы
        │     └────────────── Пароль группы (редко используется)
        └──────────────────── Имя группы
   ```

### 2.2. Команды управления пользователями и группами (Linux)

#### 1. Создание группы:
```bash
# Создание новой группы developers с автоматическим GID
sudo groupadd developers

# Создание системной группы (GID < 1000)
sudo groupadd -r sysalerts

# Просмотр созданной группы
getent group developers
```

#### 2. Создание пользователя:
```bash
# Правильный production-способ через useradd:
# -m : создать домашний каталог (/home/alex)
# -s : задать командный shell (/bin/bash)
# -c : указать описание / ФИО
# -g : основная группа
# -G : дополнительные группы (через запятую)
sudo useradd -m -s /bin/bash -c "Alex Dev" -g developers -G sudo alex

# Установка пароля для созданного пользователя:
sudo passwd alex

# Создание сервисного пользователя без входа в интерактивный шелл (nologin):
sudo useradd -r -s /usr/sbin/nologin -c "CI/CD Runner" gitlab-runner
```

#### 3. Модификация и аудит пользователя:
```bash
# Проверка текущего пользователя, UID, GID и всех групп:
id alex
whoami

# Добавление пользователя в дополнительную группу (-a ОБЯЗАТЕЛЕН, иначе удалит из остальных!):
sudo usermod -aG docker alex

# Блокировка учетной записи (добавляет '!' перед хэшем в /etc/shadow):
sudo usermod -L alex

# Разблокировка учетной записи:
sudo usermod -U alex

# Удаление пользователя вместе с его домашней директорией и почтовым ящиком:
sudo userdel -r alex
```

### 2.3. Матрица прав доступа POSIX (Классические права)

Каждый файл и директория имеют трех субъектов прав: **User (Владелец)**, **Group (Группа-владелец)**, **Others (Все остальные)**.

| Бит | Символ | Число | Для файла | Для директории |
| :---: | :---: | :---: | :--- | :--- |
| **Read** | `r` | **4** | Чтение содержимого файла | Просмотр списка файлов (`ls`) |
| **Write** | `w` | **2** | Модификация/запись файла | Создание/удаление файлов внутри каталога |
| **Execute** | `x` | **1** | Запуск файла как программы/скрипта | Вход в каталог (`cd`) и доступ к метаданным |

#### Восьмеричный расчет (Octal Notation):
* `rwx` = $4 + 2 + 1 = 7$ (полный доступ)
* `rw-` = $4 + 2 + 0 = 6$ (чтение и запись)
* `r-x` = $4 + 0 + 1 = 5$ (чтение и исполнение)
* `r--` = $4 + 0 + 0 = 4$ (только чтение)
* `---` = $0$ (нет доступа)

```bash
# Смена владельца и группы:
sudo chown alex:developers /srv/project

# Рекурсивная смена владельца:
sudo chown -R alex:developers /srv/project

# Назначение прав: Владелец = rwx (7), Группа = r-x (5), Остальные = ничего (0)
sudo chmod 750 /srv/project
```

#### Специальные биты безопасности (SUID, SGID, Sticky Bit):
1. **SUID (Set User ID, 4xxx):** файл выполняется с привилегиями своего владельца, а не запустившего его пользователя (пример: `/usr/bin/passwd` имеет права `-rwsr-xr-x`, что позволяет обычному пользователю обновлять `/etc/shadow`).
2. **SGID (Set Group ID, 2xxx):** 
   - На каталоге: **все новые файлы внутри каталога автоматически наследуют группу каталога**, а не основную группу создавшего их пользователя! Это основа совместной работы команд:
     ```bash
     sudo chmod 2775 /srv/shared_project   # Установка SGID на каталог
     ```
3. **Sticky Bit (1xxx):** устанавливается на общедоступные каталоги (например, `/tmp` с правами `drwxrwxrwt`). Удалить или переименовать файл может **только его создатель** или root, даже если у других есть право записи в каталог!
   ```bash
   sudo chmod +t /srv/public_drop
   ```

### 2.4. Расширенные списки контроля доступа POSIX ACL (`setfacl` / `getfacl`)
Когда стандартных `u/g/o` недостаточно (например, нужно дать доступ конкретному стажеру `anna` к файлу, принадлежащему `alex:developers`):

```bash
# Просмотр текущих ACL:
getfacl /srv/project/config.env

# Предоставление персональных прав чтения/записи пользователю anna:
sudo setfacl -m u:anna:rw- /srv/project/config.env

# Удаление прав пользователя из ACL:
sudo setfacl -x u:anna /srv/project/config.env

# Назначение прав по умолчанию для всех будущих файлов в каталоге (Default ACL):
sudo setfacl -d -m g:developers:rwx /srv/project
```

## 3. Руководство по выполнению для macOS (Darwin / XNU)

### 3.1. Архитектурная специфика macOS
* macOS построена на ядре XNU и подсистеме BSD, но **не использует `/etc/passwd`** для авторизации пользователей.
* Локальные учетные записи хранятся в службе каталогов **Open Directory** (база plist-файлов в `/var/db/dslocal/nodes/Default/users/`).
* Основные консольные инструменты: утилита администрирования каталога **`dscl`** и официальная сервисная утилита **`sysadminctl`**.

---

### 3.2. Управление через `sysadminctl` (Рекомендуемый современный способ в macOS)

```bash
# 1. Создание стандартного пользователя с домашней папкой:
sudo sysadminctl -addUser devuser -fullName "Developer User" -password "SecurePass123!" -home /Users/devuser

# 2. Создание администратора (добавляет в группу admin):
sudo sysadminctl -addUser sysadmin -fullName "System Admin" -password "AdminPass123!" -admin

# 3. Удаление пользователя:
sudo sysadminctl -deleteUser devuser
```

---

### 3.3. Низкоуровневое управление через `dscl` (Directory Service command line)

```bash
# 1. Просмотр списка локальных пользователей:
dscl . -list /Users

# 2. Создание пользователя пошагово через Open Directory:
# Создаем запись:
sudo dscl . -create /Users/testdev
# Задаем командную оболочку zsh:
sudo dscl . -create /Users/testdev UserShell /bin/zsh
# Задаем полное имя:
sudo dscl . -create /Users/testdev RealName "Test Developer"
# Задаем уникальный идентификатор (UID > 500 для обычных пользователей):
sudo dscl . -create /Users/testdev UniqueID 510
# Основная группа (20 = staff):
sudo dscl . -create /Users/testdev PrimaryGroupID 20
# Путь к домашней директории:
sudo dscl . -create /Users/testdev NFSHomeDirectory /Users/testdev
# Задаем пароль:
sudo dscl . -passwd /Users/testdev "Pass456!"
# Создаем физический каталог и выставляем права:
sudo createhomedir -c -u testdev

# 3. Управление группами:
# Создаем группу devteam:
sudo dscl . -create /Groups/devteam
sudo dscl . -create /Groups/devteam PrimaryGroupID 1050
# Добавляем пользователя testdev в группу devteam:
sudo dscl . -append /Groups/devteam GroupMembership testdev

# 4. Проверка состава группы:
dscl . -read /Groups/devteam GroupMembership
```

---

### 3.4. Списки контроля доступа macOS ACL
macOS поддерживает расширенные списки доступа в формате NFSv4:

```bash
# Выдача пользователю testdev прав чтения и записи на файл:
chmod +a "testdev allow read,write" /path/to/shared_doc.txt

# Просмотр прав вместе с ACL:
ls -le /path/to/shared_doc.txt

# Удаление первой записи ACL:
chmod -a# 0 /path/to/shared_doc.txt
```

## 4. Руководство по выполнению для WINDOWS (PowerShell & CMD)

### 4.1. Архитектура безопасности Windows NT
1. **SID (Security Identifier):** уникальный двоичный идентификатор переменной длины, выдаваемый каждой учетной записи и группе при создании (например, `S-1-5-21-3623811015-3361044348-30300820-1001`). Даже если переименовать пользователя, его SID не изменится. Если удалить и создать с тем же именем — будет сгенерирован **новый SID**.
2. **Access Token (Маркер доступа):** выдается пользователю в момент входа (Logon). Содержит SID пользователя, SID всех групп, в которых он состоит, и назначенные привилегии (User Rights).
3. **DACL (Discretionary Access Control List):** список в дескрипторе безопасности файла/папки, состоящий из записей **ACE (Access Control Entry)**: *«Разрешить (Allow) или Запретить (Deny) субъекту SID операцию X»*. Правило **Deny всегда имеет приоритет над Allow**!

---

### 4.2. Управление пользователями в Windows PowerShell (Рекомендуемый стандарт)

Запустите **PowerShell от имени Администратора**:

```powershell
# 1. Создание нового локального пользователя с надежным паролем:
$Password = ConvertTo-SecureString "P@ssw0rd2026!" -AsPlainText -Force
New-LocalUser -Name "DevUser1" -Password $Password -FullName "Senior Developer" -Description "Учетная запись для стенда разработки"

# 2. Просмотр параметров пользователя и его SID:
Get-LocalUser -Name "DevUser1" | Select-Object Name, FullName, Enabled, SID, PasswordRequired, PasswordLastSet | Format-List

# 3. Создание локальной группы разработчиков:
New-LocalGroup -Name "DevGroup" -Description "Группа разработчиков ПО"

# 4. Добавление пользователя в группу:
Add-LocalGroupMember -Group "DevGroup" -Member "DevUser1"

# 5. Проверка участников группы:
Get-LocalGroupMember -Group "DevGroup"

# 6. Блокировка и разблокировка пользователя:
Disable-LocalUser -Name "DevUser1"
Enable-LocalUser -Name "DevUser1"

# 7. Принудительное требование смены пароля при следующем входе:
Set-LocalUser -Name "DevUser1" -PasswordNeverExpires $false
```

### 4.4. Глубокое управление правами файловой системы NTFS (`icacls`)

В Windows файловая система NTFS кардинально отличается от POSIX: права наследуются от родительской папки вниз по иерархии.

```powershell
# Создаем рабочую директорию проекта:
New-Item -ItemType Directory -Path "C:\Project" -Force

# 1. Просмотр текущих прав доступа (DACL):
icacls "C:\Project"

# 2. Отключение наследования прав от диска C: с удалением унаследованных прав:
# /inheritance:r - удаляет унаследованные ACE
icacls "C:\Project" /inheritance:r

# 3. Выдача полного доступа Администраторам и СИСТЕМЕ:
icacls "C:\Project" /grant "SYSTEM:(OI)(CI)F"
icacls "C:\Project" /grant "Администраторы:(OI)(CI)F"

# 4. Выдача группе разработчиков прав на изменение (Modify):
# (OI) = Object Inherit (наследуют файлы)
# (CI) = Container Inherit (наследуют подкаталоги)
# M = Modify (чтение, запись, изменение, удаление файлов)
# R = Read and Execute (только чтение и запуск)
icacls "C:\Project" /grant "DevGroup:(OI)(CI)M"

# 5. Выдача стажеру JuniorDev прав ТОЛЬКО на чтение:
icacls "C:\Project" /grant "JuniorDev:(OI)(CI)R"

# 6. Явный запрет записи (Deny - имеет абсолютный приоритет!):
icacls "C:\Project\prod_release.exe" /deny "DevGroup:W"
```

## 5. Практическое лабораторное задание (Hands-on Lab)

### 🏢 Сценарий: Развертывание среды IT-компании «DevOps Lab»

Вам необходимо развернуть ролевую модель доступа для проекта веб-портала со следующей структурой:
1. **Группа `developers`:** имеет право создания, редактирования и удаления файлов проекта.
2. **Группа `qa_engineers`:** имеет доступ **только для чтения** к исходным кодам и файлам проекта, но имеет отдельную папку `qa_reports` с полным доступом для выгрузки логов и отчетов тестирования.
3. **Конфиденциальный файл `database.conf` (или `appsettings.json`):** доступен **только системному администратору / root**, все остальные пользователи не имеют к нему доступа (права `600` в Linux или запрет в Windows DACL).

1. В консоли PowerShell создать локальные группы `DevsGroup` и `QAGroup`.
2. Создать пользователей `IvanDev` и `OlgaQA` со случайными паролями и флагом `$PasswordNeverExpires = $true`.
3. Добавить пользователей в соответствующие группы.
4. Создать каталог `C:\WebAppProject`.
5. С помощью утилиты `icacls`:
   - Отключить наследование прав (`/inheritance:r`);
   - Выдать права `F` (Full Access) локальным Администраторам;
   - Выдать группе `DevsGroup` права `(OI)(CI)M` (Modify);
   - Выдать группе `QAGroup` права `(OI)(CI)R` (Read and Execute);
6. Внутри создать файл `C:\WebAppProject\db_secrets.json` и удалить из его DACL группу `QAGroup` и `DevsGroup`, оставив доступ только Администраторам.
7. Продемонстрировать результат выполнения команд `Get-LocalUser`, `Get-LocalGroupMember` и вывод `icacls C:\WebAppProject`.
